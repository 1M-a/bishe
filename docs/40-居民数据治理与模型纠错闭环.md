# 40 · 居民数据治理与模型纠错闭环

> 日期：2026-11-12  
> 目标：居民诉求不是“填完直接丢给模型”，而是经过可解释的数据治理；居委会办件时发现模型判断错误，能够形成可审核、可回放、可逐步复用的纠错闭环。

## 1. 总体流程

```text
居民提交
  → 入参校验与三层限流
  → 文本规范化、去噪
  → 同手机号 30 天内去重
      ├─ 命中：复用原查询码，不重复建 FDE/工单
      └─ 未命中：进入保密审查
  → 敏感信息识别与脱敏
  → 本地模型拆解；不可用时规则降级
  → 已确认纠错规则复核模型结果
  → FDE、业务项、工单/台账、居民单同链落库
  → 居委办理与人工复核
  → 错误样本登记
  → 同一规则累计 3 次确认
  → 后续同类事项自动修正并写 Agent 轨迹
```

闭环中的“迭代”当前指**经过人工确认的规则/提示层迭代**，不是后台自动训练模型权重。纠错样本可以在后续脱敏导出，用于 LoRA 或监督微调，但训练、评测和发布必须是独立的人工审批流程。

## 2. 居民数据治理

### 2.1 去噪与规范化

`app/intake.py` 在模型调用前执行确定性处理：

- Unicode NFKC：全角数字、字母转为统一形式；
- 连续空白归一；
- 重复标点压缩；
- 去掉句首、句尾常见礼貌填充语；
- 生成规范化文本 SHA-256，用于精确去重和审计摘要。

系统不改写地点、人物、时间、事件等事实。每个处理动作写入 `quality_flags`，居委复核时可以知道文本经历过什么处理。

### 2.2 去重策略

去重只在**同一手机号、最近 30 天**的居民单中执行：

| 方式 | 条件 | 处理 |
|---|---|---|
| 精确去重 | 规范化内容哈希相同 | 返回原居民单和原查询码 |
| 近似去重 | 文本不少于 8 字、相似度不低于 0.92、数字线索完全一致 | 返回原居民单和原查询码 |
| 不合并 | 手机号不同，或楼栋/单元/房号等数字不同 | 新建事项 |

数字线索采用保守策略：“1 栋灯坏了”和“2 栋灯坏了”即使文字高度相似，也不自动合并。重复命中不再创建新的 FDE、业务项、工单和居民单，只写一条不含明文手机号的去重审计。

居民端只显示“已合并到原记录”和原查询码，不展示相似度、规则名称等内部信息。

## 3. 居委纠错闭环

社区工作者在“模型纠错”页选择一个可见业务项，登记：

- 错误类型：分类错误或业务线错误；
- 触发词：能够代表该类误判、且真实出现在该事项原文中的短语；
- 原判断与正确判断；
- 纠错原因；
- 操作人、所属单位和时间。

一条纠错样本不会立即改变系统行为。规则键由以下四部分共同确定：

```text
错误类型 + 触发词 + 原结果 + 修正结果
```

同一规则必须来自 3 个不同业务项的同向确认。对同一业务项重复提交相同纠错返回 409，不计入支持数。达到门槛后，新诉求同时满足“包含触发词”和“当前模型结果等于原结果”时，系统才应用修正。

每次命中只增加一次应用数，并在 `AgentStep` 的解析步骤记录：

```text
学习规则[高空抛物]：类型 其他→隐患排查（3 次确认）
```

因此可以回答三类审核问题：谁确认的、依据是什么、哪条新事项实际使用过。

## 4. 权限与保密边界

- 居民：只能提交和凭“手机号 + 查询码”查看自己的进度；
- 社区：可查看本社区纠错样本、提交纠错；
- 物业：只能办理分给本单位的工单，不能进入纠错台；
- 街道：当前不直接改模型规则，避免监督方同时成为规则生产方；
- 管理员：具备全量权限，用于系统审计与维护。

居民文本先经过保密审查再进入模型和下游业务。审计日志中的居民身份只保留手机号尾号或稳定哈希，不记录完整手机号。RAG 文档仍执行敏感信息拒绝、提示词注入隔离、低相关降级和引用哈希校验，本闭环不会绕过既有 RAG 安全门槛。

当前演示库是单社区结构，`FdeRecord` 和 `ResidentTicket` 还没有独立 `community_id`。纠错列表已按操作人单位收窄，但可复用规则在当前单社区实例内生效。若扩展为多社区生产系统，必须先补租户字段，并把候选项、样本聚合和规则命中全部按 `community_id` 隔离。

## 5. 关键数据

### `resident_ticket`

- `normalized_text`：规范化文本；
- `content_hash`：内容哈希；
- `quality_status`、`quality_flags`：数据质量状态与处理动作；
- `duplicate_of`、`duplicate_kind`、`duplicate_score`：预留的重复关系字段。当前重复请求不新建行，因此主要通过审计记录命中关系。

### `model_feedback`

- `work_item_id`：被纠错的业务项；
- `issue_type`：`classify/route/split/noise`；当前自动复用仅开放 `classify/route`；
- `trigger`、`before_json`、`after_json`：规则条件与修正方向；
- `reason`、`actor`、`actor_org`：人工确认依据；
- `status`、`applied_count`、`applied_at`：审批状态与应用记录。

## 6. 验收与演示

专项回归：

```powershell
.\.venv\Scripts\python.exe -X utf8 scripts\smoke_feedback_loop.py
```

覆盖 38 项断言：清洗动作、精确/近似去重、楼栋差异防误合并、不同手机号隔离、社区/物业/街道权限、纠错样本敏感信息拒绝、触发词原文回指、重复纠错拒绝、三次确认门槛、第四条自动修正、Agent 轨迹、应用次数和审计脱敏。

答辩演示可按以下顺序：

1. 居民提交“您好！！！5 栋楼道灯坏了”，展示规范化后的正常受理；
2. 同手机号再次提交相同内容，展示“已合并到原记录”和原查询码；
3. 社区打开“模型纠错”，对三条“高空抛物”误分类分别确认；
4. 第四条同类诉求进入后自动从“其他”修正为“隐患排查”；
5. 打开协作轨迹，展示规则名称、修正前后结果和三次确认依据；
6. 用物业或街道账号访问纠错接口，展示 403 权限边界。

## 7. 后续代办

1. 增加规则停用、版本和回滚，避免已生效规则永久不可撤销；
2. 增加“疑似重复但仍新建”人工入口和误合并申诉；
3. 补 `community_id`，完成多社区候选项、样本和规则的租户隔离；
4. 建立离线脱敏样本导出、训练、评测、审批、发布流程，不能由在线系统直接微调；
5. 增加漂移看板：误判率、纠错率、规则命中率、撤销率和按月趋势；
6. 用真实社区脱敏数据重新标注评测，重点验证去重误合并率和纠错规则精确率。
