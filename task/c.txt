      __tablename__ = "invite_code"
      id      = db.Column(db.Integer, primary_key=True)
      code    = db.Column(db.String(16), unique=True, nullable=False, index=True)
      role    = db.Column(db.String(16), nullable=False)   # community/property/street/resident

1. 权限环路不锁死
   - admin 永不可降权（auth.py role=="admin"→全权限）；data_clear 只删非 admin
     （app/data_reset.py:219 "role IS NULL OR role<>admin"）。
   - 每角色至少一条可命中 ROLE_HOME 的路由（一次性脚本遍历 url_map 核对）。
   - register() 不允许创建 admin；gen_invites 白名单排除 admin。
   - RESIDENT_AUTH=1 下居民注册=active，无"永远 pending"锁死。
2. 死循环 / 无限重定向
   - 未登录 → login；login 成功 → ROLE_HOME（resident→portalviews.home）须返回 200（非 302）。
   - ROLE_HOME 每个端点实测 url_for 可构建（曾踩坑：portal.home 不存在导致 BuildError→500，
     已在 C-1 修复并加"端点注册自检"：遍历 url_map 逐一确认 ROLE_HOME 的值存在）。
   - active 用户不再进 pending 路径（auth.py 已处理）。
3. 数据库锁死
   - data_clear 有 PRAGMA busy_timeout=20000 + foreign_keys=OFF 隔离；
     全程 session.remove() + dispose，无残留长事务持锁。
4. 配置一致性
   - 三套 SECRET_KEY / DATABASE_URL / SITE_CODE / ORG_NAMES 各自独立且互不相同。
5. 冒烟兜底：四项冒烟 + compileall 全绿再上机试用。

六、风险与注意
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
1) 动手前与并行改动对齐：auth.py/models.py 有另一路在并行改（11-21 时间戳），改 B1/C1 前先确认。
2) 行号可漂移：以文件实际为准，先把目标文件全读一遍再改。
3) 清库与发码顺序：清库（data_clear）在前、发码在后；若清库在发码后，
   invite_code 必须先加入 data_reset.PRESERVED_TABLES。
4) 居民 phone 必填是 C 组闭环前提；漏了会出现"登录了查不到自己的单"。
5) D 组四处必须同批改完再启用；只改其一会出现页面与派单名不一致。
6) 模型效果无实质风险：改动在账号/配置/文案层，不触碰拆解/派单决策/RAG/脱敏链路，
   冒烟回归即可覆盖。
