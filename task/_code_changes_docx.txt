一个前提提醒：你之前确认过有另一路在并行改这份代码（auth.py/models.py/base.html 时间戳 11-21 晚上更新过）。动手前先跟那一路对齐改动范围，避免同一文件两边改冲突。每改一个 .py 文件后跑 python -m compileall app 确认无语法错误。

二、A 组：隔离地基（先做，纯配置）
这一组是整个方案的地基，而且几乎不用写业务逻辑——大部分是把写死的路径改成读环境变量。做完这一步，三套环境就能各自独立跑起来。

多地试用怎么扩展：复制"启动_试用版.bat"改成 5101/5102/5103，DATABASE_URL 分别指 trial_A.db / trial_B.db / trial_C.db，NOTICE_DIR 各自独立。一个地方 = 一个库 + 一个链接 + 一个密钥，物理隔离，邀请码在各库内定角色。这就是"一点一库"。
启动脚本里有两点特别容易踩坑，单独强调：
三个 SECRET_KEY 必须不同：dev 模式下三实例默认共用同一个开发密钥，会导致 A 的登录态在 B 也有效。所以每个脚本显式设一个不同的固定字符串。空库首次启动会自动建表并种入演示账号——试用库启动后要清一次演示账号（项目自带"清空业务数据"功能），再建真实账号。
三、B 组：邀请码注册（减负 + 防错的核心）
邀请码一次解决三件事：管理员不用逐人审核（只发码）、用户不填不选角色（系统按码自动带出）、区域前缀防跨区（A 地的码在 B 库无效）。当前代码完全没有这套机制，要从零加。

3.2 register.html 加邀请码字段
当前表单字段（已核对）：username / name / phone / org / password / password2，org 是自由文本框。改动：
加一个邀请码输入框 name="invite_code"，放在表单顶部，标注"必填，向管理员索取"。
org 输入框改成只读或隐藏，由邀请码带出，不让人手写（这是防错关键——写错了角色/单位就用不了）。
居民入口：加一句"居民试用请填居民邀请码（A-RES-xxxx）"，或单独一个"我是居民"切换，切到居民模式时隐藏 org 和单位字段。
3.3 app/admin.py register() 加校验
当前逻辑（已核对）：register() 在第 38 行，已经有按 IP 限流 5 次/小时（allow("register:"+ip, 5, 3600)），这段保留。在校验表单处插入邀请码逻辑：

这样管理员的工作从"逐人审核资料对不对"变成"发码 + 管码"——十几个码发下去就完事，这就是减负。

六、实施顺序与验收
按依赖顺序做：地基（A）→ 邀请码（B）→ 居民注册（C）→ 写死文案（D）。A 不做完，后面都没法验证隔离。每一步做完都验收，别攒到最后。

顺序
做完的标志（验收）
A 地基
三个 .bat 能分别打开 5000/5002/5001；用 A 库的账号 cookie 访问 B 端口显示未登录；三库数据互不相见
B 邀请码
A-COM 码注册出"A地社区"且单位自动带出；同一码第二次注册被拒；A 码拿到 B 库注册失败
C 居民注册
RESIDENT_AUTH=1 时居民不登录进不去填报页；登录后只看到自己的诉求；RESIDENT_AUTH=0 时演示版仍可免注册
D 写死文案
改配置后各区显示自己的物业名/联系人，页面再无"幸福里"字样

每改一个 .py 跑一次 python -m compileall app；每组做完用上面验收标准自测一遍，过了再进下一组。公网试用版是独立副本，代码改完后要重新发布才会更新（本机三个窗口有自动重载，会自己同步）。
